## 1. P0 瀑布流分列失效：卡片全堆进第一列

**缺陷**：`renderGroups()` 里 `renderMasonry(body, group.items)` 在 `body` 尚未挂进文档时就被调用
（挂载发生在后面两行）。瀑布流的「放进最短列」靠读 `col.offsetHeight` 判断，而**脱离文档的元素
没有布局盒，`offsetHeight` 恒为 0**。于是每一轮比较都选中第 0 列，整组卡片堆成一列。

实测（把这条浏览器契约写进 DOM 桩后复现）：

```
各列卡片数：解决问题=[3,0,0]   决策=[2,0,0]   学习=[4,0,0]
```

**为什么之前没暴露**：改造前瀑布流渲染进 `#masonry`，那是 `index.html` 里已经存在的元素，
前提天然成立。把容器下沉到分组内部后，`body` 是 `document.createElement` 出来的，
前提被破坏了——但代码看上去没有任何变化，DOM 结构、列数、卡片数全对，只有分布是错的。
单元测试和肉眼扫一眼都看不出来。

**修复**：先 `container.appendChild(section)`，再 `renderMasonry`。

**为什么同类问题还会再犯**：这不是笔误，是「分列算法依赖测量值」这个设计自带的隐含前提。
因此补了 `tests/dom_stub.js` + `tests/test_render.py`，把两条浏览器契约固化成断言：

1. 脱离文档的元素 `offsetHeight` 为 0；
2. 自身或祖先 `hidden` 的元素 `offsetHeight` 同样为 0（这条同时验证了「折叠时不建瀑布流」的必要）。

反向验证过：把修复回退成旧顺序，测试立刻报错 `[3,0,0]`。

## 2. P1 分组配色对比度不达标（WCAG AA）

**缺陷**：`--group-accent` 被同时当装饰色（色条、圆点、边框）和**文字色**（条数徽章、
选中的分类 chip、标题 hover）使用。按 WCAG 逐个色相实算，浅色主题 8 个色相里有 4 个不达标：

| 色相 | 徽章文字 / 浅底 | 标题 hover / 白底 |
| --- | --- | --- |
| 174 青 | **2.25:1** ✗ | **2.41:1** ✗ |
| 140 绿 | **2.36:1** ✗ | **2.54:1** ✗ |
| 196 天蓝 | **3.16:1** ✗ | **3.47:1** ✗ |
| 22 橙 | **3.92:1** ✗ | **4.39:1** ✗ |

深色主题另有 3 个色相落在 3.77–4.35:1。根因是绿色、青色在 L=45% 时本身就是「亮」颜色，
拿它当白底上的文字必然对比不足——同一个明度不可能同时满足装饰和文字两种用途。

**修复**：新增 `--group-accent-text`，只用于文字，明度单独取一档（浅色 70%/28%，
深色 70%/70%）。装饰用途继续用 `--group-accent`（非文字元素按 WCAG 1.4.11 只需 3:1，且色条纯装饰）。

修复后实测：浅色最差 4.89:1 / 5.23:1，深色最差 4.71:1 / 5.89:1，8 个色相全部达标。

**顺带说明**：选中态 chip 不只是靠颜色区分——同时有底色、边框和字重变化，不违反「不能仅靠颜色传达状态」。

## 3. P2 分组标题没有标题语义

**缺陷**：分组名是 `<button><span class="group-name">决策</span></button>`，
整页再也没有任何标题元素（改造前卡片标题是 `h3`，屏幕阅读器可以按标题跳转）。
5 个分组 + 12 张卡片变成一马平川，键盘和读屏用户失去最快的导航手段。

**修复**：`<h3 class="group-heading"><button class="group-toggle">…</button></h3>`。
`button` 的内容模型只允许短语内容、塞不进 `h3`，所以反过来让 `h3` 包 `button`——
既是可聚焦的折叠控件（WAI-ARIA 手风琴模式），又保留标题语义。
卡片标题相应从 `h3` 降为 `h4`，形成 h2（视图名）→ h3（分组）→ h4（卡片）的层级。

平铺视图（Skills）没有分组，卡片 h4 会跳级（h2 直下 h4）——两害相权，
跳级比把卡片伪装成分组的同级标题危害小。

## 4. P2 resize 无条件重建整个列表

**缺陷**：`resize` 处理里是 `if (state.data) render()`。移动端地址栏收放、软键盘弹起
都会触发 `resize`，而此时列数和抽屉断点根本没变。结果是无谓的整表重建：
DOM 全换、滚动位置跳动、正在聚焦的元素被销毁。

**修复**：引入布局指纹 `columnCount() + '|' + isDrawer()`，只有它变了才重建。
注意指纹必须同时包含抽屉断点（767px），否则 700→800 这种跨越会漏掉「收起抽屉」的处理。

## 5. 维持现状的取舍

| 项 | 判断 |
| --- | --- |
| `marked.parse()` 直接写入 `innerHTML`，md 里的原始 HTML 会被执行 | 内容全部来自本人仓库的一手文件，威胁模型里没有不可信输入。加 DOMPurify 等于引入第三方依赖，与「零依赖」原则冲突。**若将来接受他人的内容投稿，此项必须重新评估。** |
| `columnCount()` 用 `window.innerWidth` 而非容器宽度 | 1024–1180px 区间列宽约 230px，偏窄但可接受。改造前既有问题，不在本次范围内。 |
| `renderMasonry` 每插一张卡片就读一次 `offsetHeight` | 每张卡片一次强制重排，O(n) 次布局。12 条无感，几百条会有明显开销。真到那个量级应改为先测量后批量插入。 |
| 分组超过 8 个时色板复用 | 色板固定 8 色，第 9 个分组起开始重色。当前 5 个分组，等真有 9 个目录再说。 |
| `state.collapsed` 里的键不会随分类删除而清理 | Set 里残留几个字符串，无实际影响。 |

## 6. 方法论小结

这次真正咬人的不是写错的逻辑，而是**被悄悄破坏的前提**：

- `offsetHeight` 只有在元素已挂进文档且未被隐藏时才有意义——分列算法整个建立在这上面；
- 「先建子节点再挂父节点」在多数代码里是等价的写法，唯独在依赖测量值的场景下不等价。

所以审查时与其逐行读代码，不如先问：这段代码依赖了哪些浏览器契约？这些契约由谁保证？
一旦保证者从「HTML 里写死的元素」变成「JS 动态创建的元素」，契约就没人守了。
同理，把这类契约固化进测试桩，比写「渲染出了 3 列」这种断言有价值得多——
列一直在，问题是卡片没摊开。
