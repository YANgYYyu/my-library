# 部署与排障

本文件是部署架构、nginx 配置、定时更新与线上故障排查的唯一入口。
需求见 `docs/产品设计文档.md`，实现见 `docs/开发文档.md`，变更原因见 `docs/变更与审查记录.md`。

| 项目 | 内容 |
| --- | --- |
| 适用环境 | Debian 12、nginx、Python 3、Git |
| 站点形态 | 纯静态文件，无后端进程 |
| 默认架构 | 场景 A：nginx 直接托管 `public/`，监听 80 |
| 备选架构 | 场景 B：另开 8080 端口；场景 C：80 端口下用 `/lib/` 前缀 |
| 最后更新 | 2026-11-08 |

## 0. 先确认线上是哪一种架构

三种场景只能选一种，不能同时存在。先登录服务器执行：

```bash
sudo nginx -T | grep -nE "listen|server_name|root|alias|proxy_pass|location"
ls -l /etc/nginx/sites-enabled/
sudo git -C /data/apps/my-library log -1 --oneline
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/
```

判断规则：

- 配置里是 `root /data/apps/my-library/public;`，没有 `proxy_pass` → 场景 A。
- 是另一个端口或 `/lib/` 前缀 → 场景 B 或 C。
- 仍有 `proxy_pass http://127.0.0.1:8001;` → 旧方案残留，按第 4 节清理。
  生产环境不应依赖 `scripts/restart.sh` 启动的 `python3 -m http.server`。

## 1. 前置条件

- 服务器可访问 GitHub，已安装 `nginx`、`git`，系统自带 Python 3。
- 私有仓库 `my-library` 已存在。
- 服务器使用只读 deploy key 拉取代码。

## 2. 首次部署

### 2.1 生成并配置 deploy key

```bash
ssh-keygen -t ed25519 -f ~/.ssh/my-library_deploy -N "" -C "my-library-deploy"
cat ~/.ssh/my-library_deploy.pub
```

把公钥添加到 GitHub 仓库 Settings → Deploy keys，不勾选 Allow write access。

### 2.2 拉取代码

```bash
ssh-keyscan github.com >> ~/.ssh/known_hosts
sudo GIT_SSH_COMMAND='ssh -i ~/.ssh/my-library_deploy -o IdentitiesOnly=yes' \
  git clone git@github.com:YANgYYyu/my-library.git /data/apps/my-library
```

说明：deploy key 的路径按实际用户调整；cron 以 root 运行时使用 `/root/.ssh/`。

### 2.3 构建

```bash
cd /data/apps/my-library
sudo python3 build.py
```

预期输出 `已生成 .../public/data.json: N prompts, M skills`。
`public/data.json` 是构建产物，不在版本库中；全新克隆必须先构建，否则页面提示数据加载失败。

## 3. 场景 A：nginx 直接托管（默认）

创建 `/etc/nginx/sites-available/my-library`：

```nginx
server {
    listen 80 default_server;
    server_name _;

    root /data/apps/my-library/public;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }

    # 这四个文件每次部署都会变，禁用缓存；vendor/ 下的 marked 走默认缓存。
    location ~* ^/(index\.html|app\.js|style\.css|data\.json)$ {
        add_header Cache-Control "no-store, must-revalidate";
        try_files $uri =404;
    }
}
```

启用并检查：

```bash
sudo ln -s /etc/nginx/sites-available/my-library /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx
```

### 3.1 必须处理的 `default_server` 陷阱

`server_name _;` 不是通配符，它只是一个匹配不到的主机名。决定「访问 IP 时由谁接」的
是 `listen ... default_server`。Debian 自带的 `/etc/nginx/sites-enabled/default`
通常带 `listen 80 default_server;`，会抢走请求，表现为**整页空白**。

处理方式（二选一）：

- 删除默认站点：`sudo rm /etc/nginx/sites-enabled/default`；
- 或确认自己的块带 `default_server`，且没有第二个 `default_server`。

修改后必须 `sudo nginx -t && sudo systemctl reload nginx`。

## 4. 场景 B / C：与另一个项目共用一台服务器

### 4.1 场景 B：另开端口（推荐备选）

复制场景 A 的 server 块，改 `listen 8080;`（去掉 `default_server`），
`root` 仍指向 my-library；另一个项目继续占用 80。
访问 `http://<服务器IP>:8080/`。两个项目各自静态托管，互不影响，不需要常驻进程。

### 4.2 场景 C：只允许 80 端口，用路径前缀

仅当另一项目已占用 80 且不能加端口时使用。`index.html` 与 `app.js` 全部使用相对路径，
放在 `/lib/` 下可以正常工作；该方案未在真实服务器验证，使用前先按第 8 节冒烟。

```nginx
location = /lib {
    return 301 /lib/;
}

location /lib/ {
    alias /data/apps/my-library/public/;
    index index.html;
}
```

注意：

- 不要再使用 `proxy_pass` 到 8001。旧方案需要常驻一个 `http.server` 进程，
  进程退出站点就不可用，和「无常驻应用」的部署目标冲突。
- `/lib/` 下的缓存头未验证；若沿用场景 A 的 `no-store`，需要为前缀单独写 location，
  并在服务器上确认 `data.json` 不会读到旧副本。

## 5. 定时更新

root 的 crontab：

```cron
*/5 * * * * cd /data/apps/my-library && git checkout -- . && GIT_SSH_COMMAND='ssh -i /root/.ssh/my-library_deploy -o IdentitiesOnly=yes' git pull --ff-only && python3 build.py
```

说明：

- `git checkout -- .` 丢弃服务器工作区改动。构建会重写 `public/data.json`，
  若该文件曾被纳入版本管理，本地改动会让 `git pull --ff-only` 失败。
- 服务器目录不应手工修改；需要紧急改动时先提交到仓库。
- 发布延迟最长约一个 cron 周期；构建失败时页面继续使用旧产物。

## 6. 失败处理

- 构建失败：`build.py` 返回退出码 1，不写 `data.json`，线上保留旧版本。
- 拉取失败：旧版本继续服务；用 `git status` 检查工作区是否有未提交改动。
- 目录缺失或没有任何 prompts/skills 目录：构建返回 1，不会用空数据覆盖线上。
- 需要回滚：在本地 `git revert` 或 `git reset` 后推送，等待 cron 拉取并构建。

## 7. 空白页排查

### 7.1 先分清三种现象

| 现象 | 含义 | 排查方向 |
| --- | --- | --- |
| 连「Prompt & Skills」标题都没有，整页纯白 | HTML 没送到浏览器 | nginx 层 |
| 标题和侧边栏在，但内容区空白 | `app.js` 没执行 | 脚本 404/403/语法错误 |
| 显示「数据加载失败」和重试按钮 | HTML/JS 正常，`data.json` 取不到 | 构建产物或路径 |

判定依据：`app.js` 一执行就会先渲染骨架卡，失败会渲染错误面板。两者都没有，
说明脚本根本没跑起来，不要先去查 `data.json`。

### 7.2 高频原因

1. **请求命中了别的 server 块**：Debian 默认站点抢走 `default_server`；见 3.1。
2. **`root` 指错**：应指向 `public/`，不是仓库根目录。
3. **文件 403**：nginx worker 用户无权读取 `/data/apps/my-library`。
4. **`app.js` 404 / MIME 类型错误**：浏览器拒绝执行脚本。
5. **浏览器缓存了旧 `app.js`**：确认 `no-store` 已生效。
6. **`data.json` 404**：没有运行构建，或构建失败后从未生成。
7. **构建产物为空**：检查 `content/prompts`、`content/skills` 是否存在且有 Markdown 文件。

### 7.3 30 秒浏览器确认

F12 → Network，勾选 Disable cache 后刷新，确认以下请求状态码：

```
/  index.html  style.css  app.js  data.json
```

再看 Console 是否有红色报错。若 `data.json` 返回 404，先在服务器执行
`sudo python3 build.py`，再刷新。

### 7.4 服务端命令

```bash
sudo nginx -t
sudo nginx -T | grep -nE "listen|server_name|root|alias|proxy_pass"
sudo systemctl status nginx
sudo git -C /data/apps/my-library status --short
sudo git -C /data/apps/my-library log -1 --oneline
sudo ls -l /data/apps/my-library/public/data.json
```

## 8. 冒烟验证

```bash
curl -s -o /dev/null -w "/            %{http_code}\n" http://127.0.0.1/
curl -s -o /dev/null -w "/app.js      %{http_code}\n" http://127.0.0.1/app.js
curl -s -o /dev/null -w "/style.css   %{http_code}\n" http://127.0.0.1/style.css
curl -s -o /dev/null -w "/data.json   %{http_code}\n" http://127.0.0.1/data.json
curl -s -o /dev/null -w "/vendor/marked.min.js      %{http_code}\n" http://127.0.0.1/vendor/marked.min.js
curl -s -o /dev/null -w "/vendor/dompurify.min.js   %{http_code}\n" http://127.0.0.1/vendor/dompurify.min.js
```

预期全部 200；`data.json` 内容应包含 `"prompts"` 与 `"skills"`。
场景 C 把 `/` 换成 `/lib/`。

## 9. 从旧部署方式迁移

如果服务器此前把 `public/data.json` 纳入过版本管理：

```bash
cd /data/apps/my-library
sudo git checkout -- .
sudo GIT_SSH_COMMAND='ssh -i /root/.ssh/my-library_deploy -o IdentitiesOnly=yes' \
  git pull --ff-only
sudo python3 build.py
sudo git status --short   # 预期无输出
```

之后 cron 条目不变。`public/data.json` 已加入 `.gitignore`，不再入库。

## 10. 已知边界

- 本机没有服务器 SSH 配置，线上实际架构无法从本地验证；第 0 节是必须先做的确认步骤。
- 没有域名与 HTTPS；当前 HTTP 直出。获得域名后再补证书与 443。
- 场景 C 未验证；若线上实际是 `/lib/` 反代，需要先改为静态托管或补 systemd 托管，
  再删除旧的 `proxy_pass`。
