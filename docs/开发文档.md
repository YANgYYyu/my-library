## 1. 目标与范围

本网站是一个个人专用的静态站点，用于保存常用 prompt 和常用 skill。

本期范围：

- 实现 Prompts 与 Skills 两个列表，展示方式为瀑布流卡片。
- 实现卡片点击后的详情弹窗、复制与跳转功能。
- 实现按分类与标题拼音升序的排序、跟随系统的主题和移动端抽屉侧边栏。
- 实现内容子目录分类，分类由构建脚本从目录结构自动提取。
- 实现零依赖构建脚本与 Debian 12 服务器部署。

本期不做：

- 登录、后端、数据库。
- 搜索、标签与分类。
- HTTPS 与域名（待获得域名后补充）。

## 2. 技术选型

| 部分 | 选型 | 说明 |
| --- | --- | --- |
| 前端 | 原生 HTML/CSS/JavaScript | 无框架、无构建工具、无第三方运行时依赖 |
| 数据 | 静态 JSON 文件 | 由构建脚本生成，前端读取 |
| 构建脚本 | Python 3 标准库 | 零第三方依赖 |

| 内容存储 | Git 仓库（GitHub 私有仓库） | 本地编辑后推送 |

## 4. 内容格式规范

### 4.1 通用规则

- 每条内容一个 Markdown 文件。
- **标题一律取自文件名**（不含扩展名），文件里不再写 `title` 字段。
- 文件编码为 UTF-8。
- 可用子目录对内容分类，子目录名即 `category`，允许继续嵌套（如 `学习/写作`）。
  构建脚本递归采集分类根目录下的所有 Markdown 文件；文件直接放在分类根目录时 `category` 为空字符串。
- 内容 ID 取相对于分类根目录的路径（不含扩展名，分隔符统一为 `/`），例如 `决策/双向钢人论证`。
  因此不同分类下的同名文件不会互相覆盖。

### 4.2 Prompt 文件

位置：`content/prompts/`。

**不使用 frontmatter**，整个文件即 prompt 正文。文件开头的 `---` 会被视为残留的
frontmatter 并导致构建报错。

- 标题：文件名（不含扩展名）。
- 正文：完整 prompt，使用 Markdown 格式。
- 简介：正文的第一行，去除首尾空白后由构建脚本提取。正文为空时，简介为空字符串。

示例（文件 `content/prompts/翻译助手.md`）：

```markdown
你是一名专业的翻译。请将用户提供的中文翻译为英文，保留术语准确。
```

### 4.3 Skill 文件

位置：`content/skills/`。

因为简介与链接无法从文件名推导，skill 仍保留 frontmatter。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| intro | 是 | 简介 |
| url | 是 | GitHub 页面链接 |

- 标题：文件名（不含扩展名）。frontmatter 里即使写了 `title` 也会被忽略。
- 正文：本期不使用，保持为空。

示例（文件 `content/skills/grill-me.md`）：

```markdown
---
title: grill-me
intro: 用于压力测试计划或设计方案的访谈技能。
url: https://github.com/example/grill-me
---
```

## 5. 数据接口

构建脚本输出 `public/data.json`，结构如下：

```json
{
  "prompts": [
    {
      "id": "解决问题/第一性原理",
      "title": "第一性原理",
      "category": "解决问题",
      "intro": "我想解决的问题是：【填写你的问题】。",
      "body": "我想解决的问题是：【填写你的问题】。\n\n请用第一性原理把它拆回最底层。"
    }
  ],
  "skills": [
    {
      "id": "grill-me",
      "title": "grill-me",
      "category": "",
      "intro": "用于压力测试计划或设计方案的访谈技能。",
      "url": "https://github.com/example/grill-me"
    }
  ]
}
```

字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string | 相对分类根目录的路径，不含扩展名（如 `决策/双向钢人论证`） |
| title | string | 标题，取文件名（不含扩展名），与所在目录无关 |
| category | string | 分类，取自子目录名；无分类时为空字符串 |
| intro | string | 简介（prompt 为正文第一行，skill 为 frontmatter 的 intro） |
| body | string | prompt 的完整正文（skill 无此字段） |
| url | string | skill 的 GitHub 链接（prompt 无此字段） |

`data.json` 保持文件读取顺序；排序由前端完成。

## 6. 构建脚本设计

`build.py` 使用 Python 3 标准库，不引入第三方依赖。

执行动作：

1. 递归遍历 `content/prompts/` 下的所有 Markdown 文件（含子目录）。
2. 递归遍历 `content/skills/` 下的所有 Markdown 文件（含子目录）。
3. prompt 直接以整个文件作为正文，标题取文件名；skill 解析 frontmatter 取 `intro` 与 `url`。
4. 按第 5 节结构生成数据，`category` 取自所在的子目录名。
5. 将结果写入 `public/data.json`，编码为 UTF-8，不做 ASCII 转义。

prompt 规则：

- 不使用 frontmatter。若文件开头存在 `---` 包围的字段块，视为残留格式并报错。
- 简介取正文第一行（跳过开头的空行）。

skill 的 frontmatter 解析规则：

- 文件前两行必须为 `---`，否则报错并跳过该文件。
- `键: 值` 的键与值之间以英文冒号加一个空格分隔。
- 未知键忽略（包括 `title`）；缺失 `intro` 或 `url` 时，报错并跳过该文件。

失败与告警规则（出现任一条时不写 `data.json`，返回退出码 1）：

- 任何文件解析失败，都会在 stderr 输出该文件路径与原因。
- 内容 ID 重复时报错。ID 为相对路径，正常情况下不会重复。
- 分类目录存在却找不到任何 Markdown 文件时报错，避免内容被静默漏掉。

## 7. 前端设计

### 7.1 页面结构

`index.html` 包含：

- 侧边栏：站点标题「Prompt & Skills」、Prompts 与 Skills 两个导航入口、移动端关闭按钮。
- 内容区：瀑布流卡片容器。
- 弹窗：详情弹窗容器，包含关闭按钮。
- 移动端汉堡按钮：位于页面左上角，点击后滑出侧边栏。

### 7.2 瀑布流

- 不使用第三方库。
- 页面加载后按容器宽度计算列数：桌面 2 至 3 列，移动端 1 列。
- 卡片按拼音排序后的顺序，依次放入当前高度最短的列，保持横向阅读顺序。
- 卡片高度由内容自然撑开，不截断、不等高。
- 卡片底部展示分类标签，无分类时不显示。

### 7.3 排序

- 先按 `category` 拼音升序，同分类内再按 `title` 拼音升序，使用 `Intl.Collator('zh')`。
- 这样同一分类的卡片在瀑布流中会聚在一起。
- Prompts 与 Skills 两个列表分别排序。

### 7.4 详情弹窗

Prompt 弹窗：

- 标题下方展示分类标签，无分类时隐藏。
- 使用 marked 将正文渲染为 HTML。
- 提供「复制原始 Markdown」按钮，复制内容为 `body` 原文，而非渲染后的 HTML。

Skill 弹窗：

- 展示 `intro` 简介。
- 提供「打开 GitHub」按钮，点击后以新标签页打开 `url`。

复制使用 `navigator.clipboard.writeText`。浏览器不支持剪贴板 API 时，降级为选中文本复制。

### 7.5 主题

- 使用 CSS 自定义属性定义深色与浅色两套配色。
- 通过 `prefers-color-scheme` 跟随系统，不提供手动切换。

### 7.6 移动端

- 侧边栏默认隐藏，点击汉堡按钮以抽屉形式滑出。
- 抽屉打开时，背景内容不可滚动。
- 点击导航入口后，抽屉自动收起。
- 弹窗在移动端占满可用宽度。

### 7.7 依赖

- marked 以本地文件形式放在 `public/vendor/`，页面通过相对路径引用，不访问外部网络。

## 8. 本地开发与预览

前置条件：本机已安装 Python 3。

操作步骤：

1. 按第 4 节格式编辑 `content/` 下的 Markdown 文件。
2. 运行 `python3 build.py`。预期结果：`public/data.json` 更新。
3. 运行 `bash scripts/restart.sh`。预期结果：浏览器访问 `http://localhost:8001` 可预览站点。
   停止服务运行 `bash scripts/stop.sh`。预览端口固定为 8001，由脚本内的 `PORT` 变量定义。
4. 预览通过后，提交并推送。预期结果：GitHub 仓库 main 分支包含本次修改。

说明：预览必须通过 HTTP 访问，直接双击打开 `index.html` 时，浏览器会因 `file://` 协议禁止读取 `data.json`。

说明：`public/data.json` 是构建产物，已加入 `.gitignore`，不随提交进入仓库。
本地与服务器都在拉取代码后自行运行 `python3 build.py` 生成，因此提交时只需关注 `content/` 下的内容变更。

## 9. 测试

`build.py` 使用 Python 标准库 `unittest` 编写单元测试，文件为 `tests/test_build.py`。

测试覆盖：

- frontmatter 解析：正常字段、缺失必填字段、未知键（skill）。
- 标题取自文件名：prompt 与 skill 均如此，skill frontmatter 里的 `title` 被忽略。
- prompt 简介提取：正文第一行、跳过开头空行、空正文。
- prompt 残留 frontmatter 时报错。
- skill 字段输出：title、intro、url、category。
- 子目录采集：递归收集、分类取值、嵌套分类、顶层文件分类为空。
- 内容 ID：不同分类下的同名文件均被保留，跨类型 ID 重复时报错。
- 分类目录存在但无 Markdown 文件时报错。
- `data.json` 输出：结构完整、UTF-8 编码、中文不转义。

运行方式：

```bash
python3 -m unittest discover tests
```

前端部分不引入测试框架，使用产品设计文档第 8 节的验收标准进行手工验证。

## 10. 部署

### 10.1 前置条件

- 服务器系统为 Debian 12，Python 3 已安装。
- 已登录 GitHub，私有仓库 `my-library` 已存在。
- 服务器可访问 GitHub（域名 github.com）。

### 10.2 安装 nginx 与 git

1. 更新软件包索引：`sudo apt update`。
2. 安装 nginx 与 git：`sudo apt install -y nginx git`。

预期结果：`nginx -v` 与 `git --version` 均可输出版本信息。

### 10.3 配置只读 deploy key

deploy key 只用于服务器拉取代码，不授予写入权限。

1. 生成密钥：`ssh-keygen -t ed25519 -f ~/.ssh/my-library_deploy -N "" -C "my-library-deploy"`。
2. 查看公钥：`cat ~/.ssh/my-library_deploy.pub`。
3. 在 GitHub 仓库页面打开 Settings → Deploy keys → Add deploy key，粘贴公钥，不勾选 Allow write access。

预期结果：GitHub 显示该 deploy key 已添加。

### 10.4 克隆仓库并构建

1. 将 GitHub 主机指纹加入 known_hosts：`ssh-keyscan github.com >> ~/.ssh/known_hosts`。
2. 克隆仓库，显式指定 deploy key。服务器当前没有其他 GitHub 证书，必须使用该密钥：

```bash
sudo GIT_SSH_COMMAND='ssh -i ~/.ssh/my-library_deploy -o IdentitiesOnly=yes' git clone git@github.com:YANgYYyu/my-library.git /data/apps/my-library
```

3. 构建站点：`cd /data/apps/my-library && sudo python3 build.py`。

预期结果：`/data/apps/my-library/public/data.json` 存在，内容为 UTF-8 JSON。

注意：`public/data.json` 是构建产物，**不在版本库中**。克隆后必须先执行构建，
否则 nginx 会返回 404，页面显示「数据加载失败」。

### 10.5 配置 nginx

1. 创建站点配置 `/etc/nginx/sites-available/my-library`：

```nginx
server {
    listen 80;
    server_name _;
    root /data/apps/my-library/public;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }

    # 数据文件每 5 分钟更新，禁用缓存，避免浏览器读到旧内容
    location = /data.json {
        add_header Cache-Control "no-store, must-revalidate";
    }
}
```

2. 启用站点：`sudo ln -s /etc/nginx/sites-available/my-library /etc/nginx/sites-enabled/`。
3. 检查配置：`sudo nginx -t`。
4. 重载配置：`sudo systemctl reload nginx`。

预期结果：`nginx -t` 输出 syntax is ok；浏览器访问 `http://<服务器IP>/` 可看到站点。

说明：`data.json` 每 5 分钟被重新生成，默认的缓存策略可能让浏览器继续用旧副本，
表现为「内容更新了但页面没变」或「分类标签不显示」。给 `data.json` 加上 `no-store`
可以从服务端根治；首次排查时也可以先对页面做一次强制刷新（macOS `Cmd+Shift+R`、
Windows `Ctrl+F5`）来区分是缓存还是部署问题。

### 10.6 配置定时更新

1. 打开 root 的 crontab：`sudo crontab -e`。
2. 添加以下条目：

```cron
*/5 * * * * cd /data/apps/my-library && git checkout -- . && GIT_SSH_COMMAND='ssh -i /root/.ssh/my-library_deploy -o IdentitiesOnly=yes' git pull --ff-only && python3 build.py
```

说明：

- crontab 以 root 运行，密钥路径使用 `/root/.ssh/`。
- `git checkout -- .` 用于丢弃服务器工作区的本地改动。构建脚本每次都会重写
  `public/data.json`，若该文件曾被纳入版本管理，本地改动会导致 `git pull` 直接失败
  （`Your local changes would be overwritten`）。服务器目录不应直接修改文件，
  因此先恢复工作区是安全的。

预期结果：本地推送后，服务器在 5 分钟内完成拉取与构建。

### 10.7 从「data.json 入库」切换到「data.json 不入库」

若服务器此前已经按旧方式部署（`public/data.json` 曾被提交），需要额外处理一次，
否则首次 `git pull` 会因该文件存在本地改动而失败。

1. 登录服务器，进入项目目录：`cd /data/apps/my-library`。
2. 丢弃工作区本地改动：`sudo git checkout -- .`。
3. 手动执行一次拉取与构建，确认切换成功：

```bash
sudo GIT_SSH_COMMAND='ssh -i /root/.ssh/my-library_deploy -o IdentitiesOnly=yes' git pull --ff-only && sudo python3 build.py
```

4. 确认 `public/data.json` 已不再被跟踪，且站点可正常访问：

```bash
sudo git status --short    # 预期：无输出，data.json 不再出现在变更里
sudo ls -l public/data.json # 预期：文件仍存在，由构建生成
```

后续定时任务会沿用第 10.6 节的条目，无需再次干预。

### 10.8 失败处理

- 定时任务拉取或构建失败时，已发布版本保持可用，页面不回退。
- 构建失败时 `build.py` 返回退出码 1 且**不会**写入 `data.json`，磁盘上的旧文件继续生效。
- 手动验证更新流程：执行第 10.6 节 cron 条目中的命令，观察输出。
- git pull 因冲突失败时，检查本地是否存在未提交修改：`cd /data/apps/my-library && sudo git status`。服务器目录不应直接修改文件。
