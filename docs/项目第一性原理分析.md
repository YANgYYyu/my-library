## 0. 结论先行

1. **作用**：把散落在聊天记录、笔记和本地 skill 目录里的可复用指令，收敛为一份可版本化的 Markdown 语料，再用静态站点把它送到任意设备的浏览器里。站点本身不执行 prompt，只负责把文本交出去；执行发生在聊天框、编辑器或 agent 运行时。
2. **达到的效果**：取用路径缩短为「打开页面 → 点分类或卡片 → 复制原始 Markdown」；新增内容只需放入一个 `.md` 再跑一次构建；发布由 cron 自动完成；构建 0.04 秒、45 项测试 1.07 秒、零第三方运行时依赖。
3. **没有证明的效果**：没有使用数据，无法证明「因此用得更多、结果更好」。它解决的是「取得到」，不是「想得起、用得对」。

## 1. 把问题拆回最底层

### 1.1 收藏对象的本质

prompt 和 skill 都是可复用的文本指令，共同特征有四点：

- 边际复制成本接近零；
- 价值只在被调用时兑现，不被调用时价值为零；
- 会缓慢演进，但演进速度远低于使用频率；
- 出处、版本与适用边界值得记录。

因此它们不是「数据资产」，而是「工具资产」。工具资产的核心指标不是存量，而是在需要的那一刻能否被取到。

### 1.2 真正的瓶颈

存储早已不是瓶颈：聊天记录、备忘录、Obsidian 都能存。真正的瓶颈在三个环节：

| 环节 | 问题 | 本项目的处理 |
| --- | --- | --- |
| 检索 | 记得有这个方法，但找不到原文 | 分类分组、双导航、吸顶标题、拼音排序 |
| 相信 | 不知道是不是最新、有没有被改坏 | Git 版本历史；skill 标注上游链接 |
| 取用 | 找到后还要选中、复制、清格式 | 一键复制原始 Markdown |

可以把实际价值写成：**实际价值 = 内容质量 × 可达性 × 使用时机**。这是分析框架，不是实测公式。本项目把「可达性」推到接近上限，对「使用时机」几乎没有作用。

### 1.3 这个问题的基本事实

- 内容是小体积纯文本：prompt 正文合计 18.4 KB，构建产物 91.9 KB。
- 使用者只有本人；没有协作、没有写入、没有权限分级。
- 客户端只有浏览器；手机和桌面都要能打开。
- 内容变更低频：分析前 20 次提交集中在 15 天内，之后约 8 周没有新提交。
- 运行环境固定：一台 Debian 12 服务器、nginx、无域名。
- 维护者是唯一的人，且只能用碎片时间维护。

这些事实直接决定了第 3 节的形态选择。

## 2. 四分法

### 2.1 已确认、无法绕开的基本事实

1. 内容是可无损复制的文本，Markdown 足以表达。
2. 单用户、只读，意味着不需要后端、数据库、登录与写入接口。
3. 发布可以接受分钟级延迟，不需要实时。
4. 站点必须能在无域名、无 HTTPS 的 IP 直连条件下工作。
5. 维护者不愿意、也没有精力维护依赖树与构建工具链。
6. 内容一旦出错，已发布版本不能被污染。

### 2.2 习惯性接受、却没有验证过的假设

| 假设 | 若不成立会怎样 | 当前证据 |
| --- | --- | --- |
| 分类目录是合适的组织方式 | 内容增长后分类变碎，检索反而变慢 | 13 条、5 类时成立；无更大规模数据 |
| 「复制原文」是核心动作 | 若核心动作是引用或分享，缺少单条链接就是硬伤 | 需求文档如此定义；无行为数据 |
| 5 分钟发布延迟可接受 | 若编辑后要立刻看效果，得改用本地预览或手动构建 | 设计决策，未实测使用频率 |
| 静态站比现成笔记工具更合适 | 若写作、检索、同步需求更重，自建站是负资产 | 未做对照实验 |
| 公开只读没有安全风险 | 若内容含敏感信息，或将来接受他人投稿，风险成立 | 威胁模型只覆盖一手内容；`marked` 结果直接写入 `innerHTML`，无消毒 |
| 零依赖等于低维护 | 自写瀑布流、无障碍、DOM 桩的维护成本已经发生 | 审查报告记录了 P0 与多处缺陷 |

### 2.3 真正想实现的目标

按层次拆开：

- 表层，需求文档写明的：保存、查阅、复制常用内容。
- 中层，系统实际优化的：把「想到某个方法」到「把它用上」的摩擦降到最低。
- 深层，从 docs 与 memory 反推的：把个人方法沉淀为可复用资产，减少重复推导，让判断依据可追溯。

三层目标不完全一致时，项目选择了中层：界面、分组、复制、部署都围绕「取用摩擦」设计，而不是围绕「内容更多」或「功能更强」。

### 2.4 现实中的资源与约束

- 一个人维护，时间碎片化；
- 已有服务器，无域名、无 HTTPS；
- 偏好零依赖、纯文本、可迁移；
- 内容可以公开只读，但不适合做多用户产品；
- 按个人项目处理，没有可投入的预算，也不值得为 18 条内容引入基础设施。

## 3. 从约束推导形态

把约束逐条翻译成设计，能看出这个形态不是「选了某个技术栈」，而是被约束推出来的：

| 约束 | 推导出的决策 | 证据 |
| --- | --- | --- |
| 文本 + 需要版本追溯 | Markdown 文件 + Git，一条内容一个文件 | `content/`、分析前 20 次提交 |
| 单用户只读 | 无后端、无数据库、无登录 | `public/` 只有 5 个静态文件 |
| 构建期能算完的不留给运行期 | 目录 → category、文件名 → title、首行 → intro、相对路径 → id | `build.py` |
| 零依赖 | Python 标准库 + 原生 JS + 本地 marked | 无 `package.json` / `requirements.txt` |
| 取用要快 | 分组、双导航、吸顶、折叠、瀑布流、弹窗、复制原文 | `app.js`、`style.css` |
| 发布自动化 | cron 拉取 + 构建 + nginx 直出 | `docs/开发文档.md` 第 10 节 |
| 内容错误不能污染线上 | 构建失败 `exit 1`，不写 `data.json` | `build.py` 的 `main()` |
| 一个人长期维护 | 把隐含前提写进测试与文档 | `tests/`、`docs/` |

一句话概括这套架构：**Git 当数据库，构建脚本当 ETL，nginx 当只读 API，浏览器当客户端**。没有一行后端代码，但内容管理的闭环是完整的。

## 4. 实际达到了哪些效果

### 4.1 能力效果（可演示）

- **内容组织**：13 条 prompt 分布在 5 个分类（学习 4、解决问题 3、决策 2、认识你自己 2、问清问题 2）；5 条 skill 分布在 3 个分类（开发协作 3、写作 1、工具 1），全部标注上游链接。
- **新增内容成本**：把一个 `.md` 放进分类目录，跑一次 `python3 build.py`。不需要改代码，也不需要填标题和分类字段。
- **检索与取用**：分类横条与侧边栏双导航、吸顶分组标题、折叠、拼音排序、弹窗内 Markdown 渲染、一键复制原文；skill 可跳转上游仓库。
- **可用性**：移动端抽屉、跟随系统深浅色、键盘操作与焦点陷阱、加载/空/错误三态、`prefers-reduced-motion`。
- **完整性**：内容 ID 用相对路径避免重名；构建失败不覆盖上次产物；没有为了凑数保留会 404 的上游链接，已删除两条。

一个容易被忽略的取舍：拼音排序对「已知名字的查找」稳定可预测，但不表达使用顺序。当前分类名承担语义组织，界面上并没有「先问清、再学习、再解决、再决策」的引导。这不是缺陷，是「字典」与「教程」的区别。

### 4.2 成本效果（可量化）

| 指标 | 实测值 |
| --- | --- |
| 自研代码 | 2,065 行（`app.js` 813 + `style.css` 1,024 + `index.html` 48 + `build.py` 180） |
| 测试 | 4 个测试模块、45 项，全部通过，耗时 1.07 秒 |
| 构建 | 0.04 秒，产物 91.9 KB |
| 运行时第三方依赖 | 0（marked 44.7 KB 本地分发） |
| 页面资源 | 5 个文件、6 个请求，HTTP 冒烟全部 200 |
| 发布 | 1 条 cron，无常驻应用进程；正常情况下最长约 5 分钟 |
| 仓库节奏 | 分析前 20 次提交，2026-08-30 至 2026-09-13 |

这些数字说明的是**成本结构**，不是功能多少：加一条内容的边际成本接近零，故障面只有一个静态文件服务器，构建失败时页面继续使用旧版本。

### 4.3 认知与组织效果（超出原始需求）

- **把「为什么」留下来了**：分析前已有 9 篇文档、约 104 KB，其中 3 篇审查/排查报告和 1 篇线上排障手册，记录的是判断依据，不只是操作步骤。
- **把隐含前提变成测试**：瀑布流依赖「元素已挂进文档且未被隐藏，`offsetHeight` 才有意义」。这条浏览器契约被固化进 DOM 桩，成为可复用的工程资产。
- **工具库反哺自身**：站里收藏的「第一性原理」正是本次分析与对抗性审查使用的方法；`tech-doc-style-chinese`、`neat-freak` 等 skill 也参与了站点自身的建设与收尾。这是自指闭环，不是文字游戏。
- **来源纪律**：skill 迁移时「宁可不收录，也不放会 404 的链接」，删掉了两条；展示副本与运行时 skill 明确分离、独立演进。

### 4.4 不能证明的效果

1. **没有使用数据**。没有埋点、没有复制计数、仓库内没有访问日志。无法回答「是否更常用」「节省了多少时间」。
2. **线上状态未在本机验证**。本机没有服务器 SSH 配置，只能确认本地 HEAD 与 `origin/main` 指向同一提交。部署文档与 cron 配置是否按文档执行，需要服务器侧确认。
3. **最近的静止不能解释为成功或失败**。最后一条提交在 2026-09-13，之后约 8 周没有变化。对于工具，稳定即成功；但如果已停用，信号完全相同。没有使用数据时，两者不可区分。
4. **文档与事实有漂移**：文档写 12 条 prompt / 2 条 skill，实际为 13 / 5；测试数写 28 或 43，实际为 45；`开发文档` 的 7.4 标题与内容不符、7.9 重复；目录树里仍列已删除的 `legacy-deploy-to-git`。
5. **文档承诺强于代码**：文档说「分类目录存在却找不到 Markdown 会报错」，实测只检查 prompts/skills 根目录；单个空的分类子目录不会报错。
6. **测试有未覆盖的保证**：构建失败不写 `data.json` 由 `main()` 保证，但测试只覆盖 `collect()` 与 `write_data()`，没有直接测试 `main()`。
7. **单条内容没有稳定地址**：没有 hash 路由，也没有「复制链接」按钮；能复制的是正文，不是可回引的引用。想引用某条内容，只能让对方自己找。
8. **展示副本会与上游漂移**：skill 正文是迁移时的快照，没有版本字段或更新提示；上游更新后站点不会自动同步。

> 上述第 4–6 项已在 2026-11-08 的文档收敛与代码修复中处理；第 7–8 项仍是当前边界。
> 具体改动见 `docs/变更与审查记录.md`。

## 5. 表面修补与本质路径

### 5.1 原方案中只在修补表面的部分

前端的大部分迭代，包括配色、折叠、吸顶、无障碍与瀑布流，都在优化「检索体验」。它们让可达性从「能用」变成「顺手」，不是无效工作，但都在同一个乘数上做加法。

真正值得记住的教训来自两次事故：卡片全堆进第一列、末尾分类点了没反应。两者都不是功能缺失，而是**隐含前提被破坏**：脱离文档的元素没有高度；文档末尾没有滚动余量时，`scrollTo` 会被静默钳制。项目的对抗性审查抓的正是这一层，这比再加一个界面功能更有价值。

### 5.2 从基本事实重新推导的路径

如果目标从「收藏」升级为「用得更好」，按价值公式逐项看：

1. **可达性**：已经接近上限。下一步不是更多界面，而是入口：浏览器书签、搜索关键词、新标签页，或者把静态 `data.json` 当作 agent 可调用的内容端点。
2. **使用时机**：这是空白。可以在不引入后端的前提下，用 `localStorage` 记录「最近使用 / 常用」，让站点从分类目录变成常用工具架。
3. **内容质量**：没有度量。可以给每条内容加「适用场景 / 反例 / 上次使用效果」字段，仍然放在 Markdown 与构建模型内。
4. **规模上限**：当前 18 条不需要搜索；到 50–100 条时应加构建期索引，而不是运行时搜索服务。
5. **引用能力**：给弹窗加 hash 路由与「复制链接」，成本很低，但能补上「单条内容可被引用」的缺口。

这些路径都保持在原约束内：零依赖、单用户、静态、Git 管理。

### 5.3 这条路径成立的前提

- 真正的瓶颈是「取用」与「时机」，而不是内容质量或缺少使用场景；
- 用户愿意为每条内容多维护两三个字段；
- 内容量在可预见期内不超过搜索阈值。

### 5.4 验证它的第一步

不要先写代码。用一周时间手工记录两件事：

1. 「打开站点 → 复制 → 实际粘贴使用」的次数与场景；
2. 「想起某条内容，但没有打开站点」的次数与原因。

如果第 2 类明显更多，问题在入口与提醒，站内加功能无效；如果两类都很少，说明收藏本身不是瓶颈，应该停止扩张，把精力放回内容生产。这比任何功能清单都更能决定下一步。

## 6. 总结

- **它是什么**：一层极轻的个人工具分发层。Git 里的 Markdown 语料经构建脚本规范化，由 nginx 投递到浏览器，核心动作是「找到并复制」。
- **它达到了什么**：以约 2,000 行自研代码、零运行时依赖、0.04 秒构建和一条 cron，换来了低成本、低故障面的内容分发闭环；同时沉淀了可复用的审查方法、测试契约与排障文档。
- **它证明了什么**：一个单用户、只读、低频更新的知识工具，不需要后端、数据库和框架，也能做到好用且可维护。
- **它没有证明什么**：没有证明「收藏」改变了使用行为。站点是图书馆，不是实验室；下一步的杠杆在入口、时机和结果回写，而不在更多界面。
