# 线上空白页排查手册（my-library / nginx）

日期：2026-09-08　适用：`/data/apps/my-library`，nginx 静态托管

---

## 0. 排查前必须先确认的两件事

### 0.1 这个项目是纯静态站，没有后端进程

`public/` 下只有 4 个文件 + 一个 `vendor/`：

```
public/index.html   public/app.js   public/style.css   public/data.json   public/vendor/marked.min.js
```

`docs/开发文档.md` 10.5 节的 nginx 配置是 **直接静态托管**（`root` + `try_files`），
**没有也不需要 `proxy_pass` / `upstream`**。

> ⚠️ 因此你说的「应用进程确认处于运行状态」需要先澄清：
> - 如果指的是 **cron 的 `build.py`**——它每 5 分钟跑一次就退出，不会常驻，
>   任何时刻 `ps` 都看不到它，这是正常的。
> - 如果服务器上真的有一个常驻进程（比如有人执行了 `scripts/restart.sh` 起了
>   `python3 -m http.server 8001`），那是**本地预览脚本**，不是生产用法，
>   进程一退出站点就挂。文档推荐的是 nginx 直读 `public/`。
> - 如果 nginx 里配了 `proxy_pass`，那说明部署方式和文档不一致，请先看第 6 节。

### 0.2 分清「整页全白」还是「内容区空白」——这决定了完全不同的排查分支

`index.html` 里其实**写死了静态内容**：侧边栏的站点名「Prompt & Skills」、
导航按钮「Prompts / Skills」、以及 `<h2 id="view-title">Prompts</h2>`。
这些内容**不依赖任何 JS**。

| 现象 | 含义 | 跳到 |
| --- | --- | --- |
| **连「Prompt & Skills」标题都没有，整页纯白** | HTML 本身没正确送到浏览器（nginx 层） | 第 2 节 |
| **标题和侧边栏在，但 `#groups` 一片空白**（既没有骨架卡、也没有「数据加载失败」） | `app.js` 根本没执行 | 第 3 节 |
| **显示「数据加载失败」+ 重试按钮** | HTML/JS 都正常，是 `data.json` 取不到 | 第 4 节 |

> 判定位：`app.js` 一执行就会先 `renderSkeleton()` 画出骨架卡；`fetch` 失败会
> `renderError()` 画出「数据加载失败」。**这两样都没有 = JS 没跑起来**，
> 不要往 `data.json` 方向查。

浏览器侧 30 秒确认：

```
F12 → Network，勾选 Disable cache，Ctrl/Cmd+R 刷新，看这 5 个请求的状态码：
  /  index.html   style.css   app.js   data.json
再切 Console 看有没有红色报错
```

## 1. 原因排序（按可能性从高到低）

### A. 整页全白（HTML 都没送到）

| # | 原因 | 概率 |
| --- | --- | --- |
| A1 | 请求命中了别的 `server` 块（Debian 默认站点抢了 `default_server`） | **最高** |
| A2 | `root` 指错目录（指向仓库根，而非 `public/`） | 高 |
| A3 | 静态文件 403（nginx worker 用户无权读 `/data/apps/my-library`） | 中高 |
| A4 | 站点配置没启用 / 改完没 reload | 中 |
| A5 | 访问的是 443 但只监听了 80（或反过来） | 中 |
| A6 | 响应被错误压缩 / 编码 | 低 |

### B. 骨架在、内容区空白

| # | 原因 | 概率 |
| --- | --- | --- |
| B1 | `app.js` 404 / 403 / MIME 类型错误，脚本被浏览器拒绝执行 | **最高** |
| B2 | `app.js` 一执行就抛错（旧版文件、语法错误、浏览器兼容） | 中 |
| B3 | `vendor/marked.min.js` 缺失（只在开弹窗时才用到，不影响首屏） | 低 |

### C. 内容在但明显不对

| # | 原因 | 概率 |
| --- | --- | --- |
| C1 | 浏览器缓存了旧的 `app.js`（`no-store` 没生效） | 中 |
| C2 | 服务器代码没拉到最新（cron 的 `git pull` 失败） | 中 |

---

## 2. A 类：整页全白

### A1 请求命中了别的 server 块（最常见）

**为什么**：文档里的 `server_name _;` 里的 `_` 不是通配符，它只是一个永远匹配不到
的非法主机名。真正决定"访问 IP 时由谁接"的是 **`default_server`**。
Debian 装完 nginx 自带 `/etc/nginx/sites-enabled/default`，它带
`listen 80 default_server;`，且 `d` < `m` 会先被 include。
结果：你的 `my-library` 块只在 Host 恰好是 `_` 时才命中（永远不会），
**访问 IP 一律落到默认站点**——通常是一个几乎空白的占位页。

**验证**：

```bash
# 看完整生效配置里，谁带着 default_server
sudo nginx -T | grep -n "listen\|server_name\|root\|include"
ls -l /etc/nginx/sites-enabled/
```

**修复**（二选一）：

```bash
# 方案 1：删掉默认站点，让自己的块成为唯一
sudo rm /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx

# 方案 2：直接在自己的块上声明 default_server
#   listen 80 default_server;
```

顺带把 `server_name _;` 改成实际域名或 `server_name <你的域名或IP>;`。

### A2 root 指错目录

**验证**：

```bash
sudo nginx -T | grep -n "root"
ls -l /data/apps/my-library/public/index.html    # 文件真的在吗
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/
```

必须是 `root /data/apps/my-library/public;`（**带 `/public`**）。
指向 `/data/apps/my-library` 时，`/` 找不到 `index.html`，会 403 或 404。

**修复**：改 `root`，然后 `sudo nginx -t && sudo systemctl reload nginx`。

### A3 静态文件 403（权限）

**验证**：

```bash
# 逐层看权限，任何一层缺 x 都会 403
namei -l /data/apps/my-library/public/index.html
ps aux | grep nginx          # 看 worker 跑在哪个用户下
sudo tail -30 /var/log/nginx/error.log   # 找 "Permission denied" / "open() ... failed (13: Permission denied)"
```

**修复**：

```bash
sudo chmod o+rx /data /data/apps /data/apps/my-library /data/apps/my-library/public
sudo chmod o+r  /data/apps/my-library/public/*
sudo find /data/apps/my-library/public -type d -exec chmod o+rx {} +
```

> 本项目服务器是 root-only（无 `www-data` 账户），若 nginx 以 `www-data` 运行，
> 必须给 other 的读权限；若以 root 运行则不会 403。

### A4 配置未启用 / 未 reload

**验证**：

```bash
sudo nginx -t                       # 是否 syntax is ok
ls -l /etc/nginx/sites-enabled/     # 软链在不在
systemctl is-active nginx
```

**修复**：

```bash
sudo ln -sf /etc/nginx/sites-available/my-library /etc/nginx/sites-enabled/my-library
sudo nginx -t && sudo systemctl reload nginx
```

### A5 端口不匹配

**验证**：

```bash
sudo ss -lntp | grep -E ':80|:443'
sudo nginx -T | grep -n "listen"
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/
curl -sk -o /dev/null -w "%{http_code}\n" https://127.0.0.1/
```

用 http 访问只配了 443 的站点（或反之）会得到连接失败，不是空白页——
但如果 443 上配了错误的 `ssl_certificate`，浏览器可能渲染出空白。

### A6 压缩 / 编码异常

**验证**：`curl -sI http://127.0.0.1/ | grep -i "content-encoding\|content-type"`
若返回 `gzip` 但内容没真压缩，浏览器会解出乱码或空白。
**修复**：确认 `gzip on` 与 `gzip_types` 配置正确，或先临时关掉验证。

## 3. B 类：骨架在、内容区空白（JS 没执行）

### B1 app.js 没加载

**验证**（浏览器 Network 面板最直接）：看 `app.js` 那一行

| 状态码 | 含义 | 修法 |
| --- | --- | --- |
| 404 | 文件不在 `root` 下（多半是 A2 的 root 指错） | 修 root |
| 403 | 权限 | 见 A3 |
| 200 但 Console 报 `Refused to execute ... MIME type ('text/plain')` | nginx 把 `.js` 当纯文本返回 | 见下 |

MIME 问题的修法：确认 `/etc/nginx/mime.types` 被 include，且里面有
`application/javascript js;`：

```bash
sudo nginx -T | grep -n "include.*mime.types"
grep -n "javascript" /etc/nginx/mime.types
```

**服务器侧交叉验证**：

```bash
curl -s -o /dev/null -w "app.js   %{http_code} %{content_type} %{size_download}\n" http://127.0.0.1/app.js
curl -s -o /dev/null -w "index    %{http_code} %{content_type} %{size_download}\n" http://127.0.0.1/
curl -s -o /dev/null -w "style    %{http_code} %{content_type} %{size_download}\n" http://127.0.0.1/style.css
curl -s -o /dev/null -w "data     %{http_code} %{content_type} %{size_download}\n" http://127.0.0.1/data.json
curl -s -o /dev/null -w "marked   %{http_code} %{content_type} %{size_download}\n" http://127.0.0.1/vendor/marked.min.js
```

预期全部 `200`，`app.js` 的 `content_type` 应为 `application/javascript` 或 `text/javascript`。

### B2 app.js 一执行就抛错

**验证**：F12 Console 的红色报错，常见几种：

- `Uncaught SyntaxError` → 文件传输被截断或版本不对
- `xxx is not a function` / `Cannot read properties of undefined` → 新旧版本混用
  （`index.html` 是新的、`app.js` 是缓存的旧版）
- `Unexpected token '<'` → `app.js` 实际返回的是 HTML（root 指错，404 页面被当 JS 执行）

**修复**：

```bash
cd /data/apps/my-library
sudo git checkout -- .
sudo GIT_SSH_COMMAND='ssh -i /root/.ssh/my-library_deploy -o IdentitiesOnly=yes' git pull --ff-only
sudo python3 build.py
sudo git log --oneline -1        # 应为 56eb30a 或更新
```

### B3 vendor/marked.min.js 缺失

只在打开详情弹窗时才用到，**不会导致首屏空白**。
若弹窗里 Markdown 不渲染：确认 `public/vendor/marked.min.js` 存在（已入库，
正常 `git pull` 会带上）。

## 4. C 类：显示「数据加载失败」

这不是空白页，但常被一起报过来，单独说明。

### C1 data.json 不存在（最高频）

`public/data.json` 在 `.gitignore` 里，**不入库**。全新克隆后必须先跑 `build.py`，
否则 nginx 对它返回 404，页面显示「数据加载失败 · data.json 不存在」。

**验证**：

```bash
ls -l /data/apps/my-library/public/data.json
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/data.json
```

**修复**：

```bash
cd /data/apps/my-library && sudo python3 build.py
# 预期：[build] 已生成 .../public/data.json: 12 prompts, 2 skills
```

### C2 cron 没跑起来

**验证**：

```bash
sudo crontab -l | grep my-library
sudo tail -20 /var/log/syslog | grep CRON    # Debian 系
sudo ls -l --time-style=full-iso /data/apps/my-library/public/data.json   # 看 mtime 是否在 5 分钟内
```

**修复**：`sudo crontab -e` 补上（注意 `git checkout -- .` 不能少，
否则 `build.py` 每次重写 `data.json` 会让 `git pull --ff-only` 失败）：

```cron
*/5 * * * * cd /data/apps/my-library && git checkout -- . && GIT_SSH_COMMAND='ssh -i /root/.ssh/my-library_deploy -o IdentitiesOnly=yes' git pull --ff-only && python3 build.py
```

### C3 浏览器缓存了旧版 app.js

文档里给 `index.html / app.js / style.css / data.json` 配了 `no-store`。
**验证**：`curl -sI http://127.0.0.1/app.js | grep -i cache-control`，
应有 `no-store, must-revalidate`。没有说明配置没生效（多半是 A1/A4）。

## 5. 三分钟定位流程（复制粘贴即可）

在**服务器上**跑这一段，把输出发我：

```bash
echo "=== 1. nginx 生效配置 ==="
sudo nginx -T 2>&1 | grep -nE "listen|server_name|root |location|proxy_pass|include"

echo; echo "=== 2. 语法与运行状态 ==="
sudo nginx -t 2>&1; systemctl is-active nginx

echo; echo "=== 3. 站点目录 ==="
ls -l /data/apps/my-library/public/ 2>&1 | head

echo; echo "=== 4. 本机自测 ==="
for p in / /index.html /app.js /style.css /data.json /vendor/marked.min.js; do
  printf "%-24s " "$p"
  curl -s -o /dev/null -w "%{http_code}  %{content_type}  %{size_download}B\n" "http://127.0.0.1$p"
done

echo; echo "=== 5. 监听端口 ==="
sudo ss -lntp 2>/dev/null | grep -E ':80|:443|:8001' || echo "（80/443/8001 均无监听）"

echo; echo "=== 6. 错误日志（最后 30 行）==="
sudo tail -30 /var/log/nginx/error.log

echo; echo "=== 7. 访问日志（最后 10 行）==="
sudo tail -10 /var/log/nginx/access.log

echo; echo "=== 8. 代码版本 ==="
cd /data/apps/my-library && sudo git log --oneline -1 && sudo git status --short
```

在**浏览器**上：

1. F12 → Network → 勾选 Disable cache → 刷新
2. 看 `/`、`app.js`、`style.css`、`data.json` 四个请求的 **Status** 列
3. F12 → Console → 有没有红色报错（原文贴出来）
4. 页面上右键 → **查看网页源代码** → 里面有没有 `Prompt & Skills` 这行字
   - **没有** → HTML 都没送到，走第 2 节（A 类）
   - **有** → HTML 到了，走第 3 节（B 类）

## 6. 如果实际是「nginx 反代到后端进程」的部署方式

文档没这么配，但若服务器上确实这么做了（`scripts/restart.sh` 起了
`python3 -m http.server 8001`，nginx `proxy_pass` 过去），额外查这几项：

| 检查项 | 命令 | 正常表现 |
| --- | --- | --- |
| 进程是否真在监听 | `sudo ss -lntp \| grep 8001` | 有 `LISTEN` |
| **监听地址** | 同上，看 Local Address | `127.0.0.1:8001` 或 `0.0.0.0:8001`；若是 `127.0.0.1` 而 nginx 用外网 IP 去连则不通 |
| 后端直连是否通 | `curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8001/` | `200` |
| upstream 地址是否与监听一致 | `sudo nginx -T \| grep proxy_pass` | 端口必须完全对上 |
| 后端是否崩了 | `sudo journalctl -u <服务名> -n 50` | 无 FATAL |
| 502/504 | `sudo tail -30 /var/log/nginx/error.log` | 找 `connect() failed (111: Connection refused)` / `upstream timed out` |

**典型坑**：`python3 -m http.server` 是**前台**进程，SSH 断开就死；
它也没有 systemd 托管，重启后不会自动拉起。
若确实要用这种架构，应该写成 systemd 服务（`Restart=always`），
但**本项目推荐直接用 nginx 静态托管 `public/`，更省事也更稳**。

## 7. 需要你补充的关键信息

按重要性排序，能给几条就给几条：

1. **浏览器 Network 面板**：`/`、`app.js`、`style.css`、`data.json` 四个请求的
   **状态码**（200 / 404 / 403 / 502 …）
2. **浏览器 Console**：红色报错原文
3. **右键「查看网页源代码」**：里面有没有 `Prompt & Skills` 这行
   （区分 A 类还是 B 类，最关键的一条）
4. **服务器上 `sudo nginx -T` 的完整输出**（或至少所有 `listen` / `server_name` / `root` / `location` / `proxy_pass` 行）
5. **访问方式**：用的是 `http://<IP>`、`http://<域名>` 还是 `https://`？
   有没有配 HTTPS
6. **部署路径确认**：`/data/apps/my-library/public/` 下 `ls -l` 的输出
7. **`sudo ss -lntp`** 的输出（看 80/443/8001 谁在监听）
8. **你所说的「应用进程」到底是什么**：ps 输出贴一下。
   如果是 `python3 -m http.server`，那是预览脚本不是生产用法
9. **`sudo tail -30 /var/log/nginx/error.log`** 的内容
10. **`sudo git log --oneline -1`** 在服务器上的输出（确认代码是否已拉取，
    当前最新应为 `56eb30a`）

> 只给第 3 条也能立刻把范围砍掉一半。
