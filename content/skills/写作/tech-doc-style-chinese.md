# 中文技术文档与产品文案规范

<!-- 作者：Fenng（GitHub：@Fenng） -->

## 适用范围

将本 Skill 用于中文技术内容的撰写、改写、校对和审阅，包括：

- 文档首页、产品介绍、解决方案页和更新日志
- API 文档、参数说明、错误码和常见问题
- 操作手册、故障排查、运维 Runbook 和安全说明
- 界面文案、按钮、导航、状态和提示信息

不要改写代码字面量、JSON 键名、URL、API 路径、数据库字段名、命令、配置项或其他机器可读标识符。

## 规则优先级

发生冲突时，按以下顺序处理：

1. 保留事实、逻辑、限制、安全信息和法律含义。
2. 服从用户明确要求和目标项目约定。
3. 保持技术术语和机器可读内容准确。
4. 改善结构、语义、语气和可扫读性。
5. 最后处理标点、留白、大小写等排版细节。

不得为了句子更短、语气更确定或格式更统一而牺牲更高优先级的信息。

## 事实保真

- 不新增原文或可靠上下文没有提供的日期、数字、时限、SLA、能力、条件、因果关系或结论。
- 不删除前置条件、适用范围、例外、风险、安全警告、兼容性说明或失败处理。
- 不把可能、计划、建议、通常等不确定表达改成确定事实。
- 信息不足时保留原意，或明确标记「待确认」；不要自行补全。
- 改写引用、法规、合同、错误原文或用户提供的固定文案时，优先保持原文并将建议单独列出。

示例：

- `截止 4 月 12 日` -> `截至 4 月 12 日`
- `尽快处理` -> `在约定时限内处理〔具体时限待确认〕`
- 不要凭空补成 `截至 2026 年 4 月 12 日` 或 `30 分钟内处理`

## 先判断任务模式

### 撰写

- 先确定受众、内容类型、事实来源、发布载体和篇幅。
- 缺少会改变结论的事实时，先标记缺口，再继续组织可确认内容。

### 改写

- 保留事实、逻辑关系、信息层级、限制和必要例外。
- 默认交付完整改写稿；重大语义选择或待确认内容另行说明。

### 校对

- 只处理约定范围内的错字、标点、留白、大小写和术语一致性。
- 未经要求，不改变结构、语气或事实表达。

### 审阅

- 先列问题，再给建议；按影响程度排序并引用具体原文。
- 未经授权，不直接修改文件。

## 核心写作规则

### 语义与语气

- 准确先于修辞，清晰先于热闹。
- 使用克制、直接、可执行的中文。
- 优先说明「是什么、适用于什么、需要做什么、接着看哪里」。
- 避免问候式开场、宣传口号、空泛形容和连续堆叠黑话。
- 默认不直接称呼读者；必要时使用明确角色，如「开发者」「实施人员」。
- 第二人称、感叹号和品牌语气属于风格选择；项目约定或特定界面语境可以覆盖默认规则。

### 结构与句子

- 一个段落承载一个主要信息点。
- 一个句子保持一个清晰的主干；不要连续堆叠多个条件、动作和例外。
- 列表项保持相同层级、句式和信息密度。
- 标题反映用途，不只使用抽象名词。
- 删除重复信息，不删除事实、条件和例外。
- 指代可能不清时，用具体名称替代「该」「其」「此」「上述」。

### 术语与排版

- 同一概念使用同一首选术语，不因追求变化而替换同义词。
- 中文引号默认使用直角引号 `「」`；项目或地区规范可以覆盖。
- 在可见正文中按语义处理中文与英文、独立数字和版本号之间的留白。
- 术语、产品名和缩写优先采用项目规范或官方写法，不机械替换。
- 不直接批量运行排版替换工具；先保护 Markdown、代码和机器可读内容。

详细规则见 术语与排版（references/terminology-and-typography.md）。

## 按内容类型处理

### 入口页和介绍页

首段优先回答：

- 内容覆盖什么
- 适合谁使用
- 从哪里开始读

避免标题、正文和行动按钮重复同一信息。

### API 文档

- 请求方法、路径、字段和值使用代码环境保护。
- 参数说明一列一义，并写清类型、单位、默认值、限制和是否必填。
- 状态和错误文案根据实际语义翻译，不机械对应单个英文词。
- 写明前置条件、成功结果、失败结果和恢复方式。

详细规则见 API 状态与错误文案（references/api-status-copy.md）。

### 界面文案

- 按钮说明动作和目标，不重复页面标题。
- 错误提示说明发生了什么、影响是什么，以及如何恢复。
- 危险操作写清对象、后果和是否可撤销。
- 空状态区分「没有数据」「尚未创建」「无权限」和「加载失败」。

### 操作与故障排查

对操作手册、故障排查、运维 Runbook、安全说明和多步骤 API 流程，读取并应用 受控中文技术写作（references/controlled-technical-chinese.md）。不要把这些规则机械应用于品牌文案、叙事文本或固定引用。

## 项目覆盖规则

先检查目标项目自己的 `AGENTS.md`、术语表、品牌规范、既有文档和用户指示。不要把本 Skill 仓库中的示例约定当成目标项目约定。

需要建立项目覆盖文件时，参考 项目覆盖模板（references/project-overrides-example.md），并将实际文件放在目标项目中。

## 编辑流程

1. 确认任务模式、内容类型、受众和项目约定。
2. 标记事实、数字、限制、引用和机器可读内容，建立不可改动边界。
3. 修复语义错误、歧义、遗漏和不一致。
4. 调整信息顺序、段落、标题和列表。
5. 处理语气、术语、标点、留白和大小写。
6. 对照原文复核事实、条件、否定范围、因果关系和确定程度。
7. 运行适用的轻量检查器，并人工判断警告和风格提示。

## 最终检查

- 是否新增了来源不明的日期、数字、时限、能力或结论
- 是否遗漏了条件、例外、风险、单位、默认值或恢复方式
- 主语、对象、否定范围、因果关系和确定程度是否保持准确
- 同一概念是否使用同一术语
- 标题、正文、卡片和按钮是否重复
- 代码、路径、字段、命令和引用是否保持原样
- 内容是否便于目标读者扫读和执行
- 项目覆盖规则是否来自目标项目，而不是示例文件

## 参考资料路由

- 术语、黑话、错词、大小写、标点和中西文留白：读取 术语与排版（references/terminology-and-typography.md）

### references/terminology-and-typography.md

# 术语与排版

仅在需要处理术语、错词、标点、留白或大小写时读取本文件。所有规则只作用于可见正文，不作用于代码、路径、字段、命令、配置项和用户指定的固定字面量。

## 术语原则

- 同一概念使用同一首选术语。
- 优先采用目标项目术语表和产品官方写法。
- 不因为追求词汇变化而替换同义词。
- 词语可能有多个合法含义时，先判断语境，不做全局替换。
- 项目专属术语放在目标项目的覆盖文件中。

## 空泛表达与黑话

以下词语容易掩盖具体动作。只有在有明确业务定义、属于正式术语、引用原文或用户要求保留时才使用：

- `赋能`
- `抓手`
- `闭环`
- `沉淀`
- `对齐`
- `对标`
- `拉通`
- `打通`
- `协同`
- `联动`
- `洞察`
- `赛道`
- `心智`
- `调性`
- `战役`
- `链路`
- `势能`
- `兜底`
- `落盘`
- `收口`
- `透传`

优先说明它实际指什么：

- `赋能` -> `提供`，或直接写提供的能力
- `抓手` -> `关键措施`
- `闭环` -> `完整流程`，或列出开始、处理和完成条件
- `沉淀` -> `形成`、`积累`、`保存`
- `对齐` -> `统一`、`确认一致`
- `拉通` / `打通` -> `连接`、`贯通`
- `洞察` -> `分析结论`
- `兜底` -> 写出失败后的具体保障机制
- `落盘` -> `写入文件`、`保存到本地`
- `透传` -> `原样传给下游`

以下词语依赖语境，不应由检查器自动替换：

- `场景`
- `生态`
- `体系`
- `路径`
- `触点`
- `卡点`
- `布局`
- `矩阵`
- `颗粒度`
- `复盘`
- `梳理`
- `输出`
- `提炼`

保留内部术语时，在首次出现处说明实际含义，避免连续堆叠多个术语。

## 标点

- 中文正文默认使用全角中文标点。
- 中文引号默认使用直角引号 `「」`；项目、地区、出版或引用规范可以覆盖。
- 避免连续感叹号、省略号和口号式断句。
- 完整句式的列表项统一使用句号；短语型列表项可以不加句号，但同一列表保持一致。
- 并列词语使用顿号，并列分句根据层级使用逗号或分号。
- 冒号后应当确有解释、列举或引用，不要把每句话都拆成冒号列表。
- 破折号、括号和斜线只在关系明确时使用，不用它们代替句子组织。

## 称呼

- 技术文档默认不直接称呼读者，优先使用无主句或明确角色。
- 根据语境使用 `开发者`、`技术负责人`、`实施人员`、`业务负责人`、`产品经理`。
- `你`、`您`、`同学` 属于风格提示，不是普遍语言错误；消费产品、帮助文本或品牌规范可以允许第二人称。

## 中文与英文、数字之间的留白

在可见正文中，中文与可读的半角英文单词、英文缩写、独立数字和版本号之间通常保留空格：

- `获取批量 ID`
- `HTTP 请求`
- `版本 2.0`
- `AI 服务`
- `与 PM 协作`

不要机械处理：

- 行内代码和代码块
- JSON 键名
- URL 和 API 路径
- 数据库字段名
- 命令、配置项、占位符和正则表达式
- 直接镜像接口定义的表头
- 产品官方拼写和用户指定字面量

数字排版还应检查：

- 日期、时间和时区是否完整
- 百分比与百分点是否混用
- 数值是否带有必要单位
- 区间上下界和包含关系是否明确
- 货币、温度、存储单位和千位分隔是否一致

## 技术术语大小写

以下是常见推荐写法，不应覆盖项目或产品的官方命名：

- `id` / `Id` -> `ID`
- `http` / `Http` -> `HTTP`
- `url` / `Url` -> `URL`
- `json` / `Json` -> `JSON`
- `api` / `Api` -> `API`
- `ai` / `Ai` -> `AI`
- `javascript` -> `JavaScript`
- `typescript` -> `TypeScript`
- `llm` / `Llm` -> `LLM`
- `aigc` / `Aigc` -> `AIGC`
- `rag` / `Rag` -> `RAG`
- `chatgpt` / `Chatgpt` -> `ChatGPT`
- `openai api` / `OpenAI api` -> `OpenAI API`
- `python` -> `Python`
- `nodejs` -> `Node.js`
- `github` -> `GitHub`
- `gitlab` -> `GitLab`
- `postgresql` -> `PostgreSQL`
- `grpc` -> `gRPC`
- `graphql` -> `GraphQL`
- `websocket` -> `WebSocket`
- `yaml` -> `YAML`
- `xml` -> `XML`
- `jwt` -> `JWT`

以下写法依赖语境，只能提示人工确认：

- `JS`：简短界面或既有名称中可能合理，正式正文可写 `JavaScript`
- `H5`：可能指移动 Web 活动页，不等同于 HTML5 标准
- `Postgres`：可能是项目采用的正式简称
- `OAuth`：可能指协议家族，不能自动补成 `OAuth 2.0`
- `k8s`：正式文档可写 `Kubernetes`，命令、标签和社区语境可能保留

## 高频错词与语境词

可以作为确定错误处理：

- `阀值` -> `阈值`
- `布署` -> `部署`
- `反回` -> `返回`
- `回朔` -> `回溯`
- `做为` -> `作为`
- `embeding` -> `embedding`
- `提示工程学` -> `提示工程`

必须结合语境判断：

- `登录系统`，但可以说 `登陆月球`
- `配置参数`，但可以说 `配制溶液`
- `截至 4 月 12 日`，但可以说 `截止日期`
- `启用功能`，但可以说 `起用新人`
- `标识字段`，但可以说 `在图中标示位置`
- 技术能力通常写 `实时通信`，但 `即时` 在其他语境中可能正确
- `认证` 表示确认身份，`授权` 表示授予权限

## 数量与逻辑

- `缩小了 3 倍` -> `缩小到原来的 1/3` 或写明减少比例
- `从 20% 增长到 30%`：增加 10 个百分点，相对增长 50%
- `转化率提升了 5%`：确认是提升 5% 还是 5 个百分点
- `翻了 1 倍` -> `变为原来的 2 倍`
- `不超过 100 以上` -> `不超过 100`
- `预计大约在 3 点左右` -> `预计 3 点左右`

修正表达时不得自行补充原文没有的基数、年份、期限或测量结果。

### references/api-status-copy.md

# API 状态与错误文案

仅在撰写、翻译或审阅 API 文档、状态标签、错误码和接口提示时读取本文件。

## 基本原则

- 先确认状态在当前接口中的真实含义，再选择中文。
- 不把一个英文状态词固定映射成唯一中文。
- 保持 HTTP 状态、业务状态、任务状态和界面提示之间的区别。
- 错误文案尽量说明问题、影响和恢复方式。
- 不修改状态码、枚举值、字段名和响应原文。

## 常见状态词

- `Success`
  - 根据语义使用 `已完成`、`已处理`、`请求成功`
- `Invalid`
  - 使用 `无效`、`格式有误`、`校验未通过`
  - 不默认翻译成 `非法`
- `Available`
  - 使用 `已开通`、`可获取`、`可访问`、`可使用`
- `Unsupported`
  - 使用 `暂不支持`、`不支持该类型`、`当前不支持`
- `Pending`
  - 使用 `待处理`、`处理中`、`待确认`
- `Expired`
  - 使用 `已过期`
- `Missing`
  - 使用 `缺少`、`未提供`
- `Denied`
  - 使用 `被拒绝`、`未通过`
- `Forbidden`
  - 根据语义使用 `无权限访问`、`当前不允许访问`
- `Not Found`
  - 使用 `未找到对应内容`、`未找到对应数据`
- `Accepted`
  - 使用 `已受理`、`已接收，等待处理`
- `Completed`
  - 使用 `已完成`
- `Failed`
  - 使用 `失败`、`处理失败`
- `Conflict`
  - 使用 `状态冲突`、`资源状态不一致`、`请求与当前状态冲突`
- `Unauthorized`
  - 根据实际原因使用 `未登录`、`认证未通过`、`缺少认证信息`
  - 不机械翻译成 `未授权`
- `Bad Request`
  - 使用 `请求参数有误`、`请求格式有误`
- `Timeout`
  - 使用 `请求超时`、`处理超时`

## 参数说明

每个参数尽量写清：

- 类型和格式
- 是否必填
- 单位
- 默认值
- 允许值或范围
- 缺省行为
- 与其他参数的依赖或互斥关系

不要用「正常值」「根据情况填写」「相关信息」等无法执行的说明。

## 错误文案结构

优先按以下顺序提供信息：

1. 发生了什么
2. 哪个对象受到影响
3. 可能原因
4. 可以执行的恢复操作
5. 仍然失败时需要提供的诊断信息

不要把推测写成确定原因，也不要在没有依据时承诺恢复时间。

### references/controlled-technical-chinese.md

# 受控中文技术写作

本模块借鉴 ASD-STE100 的受控语言思路，用于降低中文技术说明中的歧义和执行风险。它不是 ASD-STE100 的中文版本，也不表示输出符合或通过 ASD-STE100 认证。

ASD-STE100 是面向英文技术文档的标准。英语受控词典、词性、时态和句长规则不能直接移植到中文。本模块只采用可迁移的方法，并根据中文句法和技术写作语境重新表述。

官方资料：

- [ASD-STE100 官方说明](https://www.asd-ste100.org/about_STE.html)
- [ASD-STE100 Issue 9 获取页面](https://www.asd-ste100.org/STE_downloads.html)
- [ASD-STE100 工具与合规说明](https://www.asd-ste100.org/STEsoftware.html)

## 适用强度

### 完整应用

- 操作手册
- 安装和部署步骤
- 故障排查
- 运维 Runbook
- 安全警告
- 多步骤 API 调用流程

### 选择性应用

- API 概念说明
- 常见问题
- 更新日志
- 产品能力说明

选择性应用术语一致、指代明确和事实保真规则，不强制把所有句子改成操作步骤。

### 不机械应用

- 品牌和落地页文案
- 叙事性文章
- 法律原文和正式引用
- 需要保留作者风格的内容
- 极短的按钮和导航标签

## 核心原则

### 1. 保留事实

- 不新增来源没有提供的数字、日期、时限、能力、条件或结论。
- 不删除警告、限制、例外、单位、默认值和失败处理。
- 不改变可能、建议、计划、通常等词表达的确定程度。

### 2. 一个概念使用一个首选术语

- 为关键对象、状态和动作确定首选术语。
- 不为了避免重复而轮换同义词。
- 首次出现的缩写给出全称；后文保持同一写法。
- 项目专属名词和动词来自目标项目术语表或可靠上下文。
- 同一个词存在多个含义时，用更具体的词消除歧义，不做机械替换。

### 3. 一个步骤包含一个主要动作

- 以明确动作开始步骤。
- 写清动作对象，不只写「处理」「操作」「执行」。
- 多个动作必须按顺序执行时，拆成编号步骤。
- 两个动作必须同时完成或构成一个不可分操作时，可以保留在同一步。
- 不为追求短句拆散必要的条件、否定和因果关系。

### 4. 条件和风险先于动作

- 读者执行动作前必须知道的条件放在动作之前。
- 警告放在可能造成风险的步骤之前。
- 条件较多时，单独列出前置条件。
- 不把关键限制放在步骤末尾的括号中。

### 5. 明确执行者、对象和结果

- 可能出现责任或指代歧义时，写出执行者。
- 明确区分系统自动行为和人工操作。
- 必要时说明预期结果，便于判断步骤是否成功。
- 不使用无法定位对象的「该」「其」「此」「上述」「相关」。

### 6. 保持逻辑顺序

- 描述操作时按实际执行顺序排列。
- 故障排查先给低风险、可逆和证据价值高的检查。
- 将原因、现象、操作和结果分开，不混在一个长句中。
- 否定范围必须明确，避免读者无法判断禁止的是哪个动作。

## 操作步骤模板

在适用时按以下结构组织：

1. 前置条件
2. 风险或限制
3. 编号操作步骤
4. 每一步的预期结果
5. 失败时的停止条件和恢复方式

不要补造原文没有的预期结果或恢复步骤。资料缺失时标记「待确认」。

## 故障排查模板

1. 说明可观察到的现象。
2. 说明需要收集的日志、状态或错误码。
3. 按证据和风险安排检查顺序。
4. 对每项检查写明判断条件。
5. 只有证据支持时才给出原因。
6. 写明恢复操作、验证方式和停止条件。

不要把「可能原因」改写成「确定原因」。

## 回归样例

以下样例用于检查事实保真、条件顺序、动作边界和过度简化风险。改写后不得增加样例原文没有的信息。

### 操作手册

#### 样例 1

改写前：

`在安装代理程序之前需要确认服务器能够访问更新地址，然后运行安装命令。`

改写后：

1. `确认服务器能够访问更新地址。`
2. `运行安装命令。`

检查点：条件位于动作之前，没有增加网络地址或命令。

#### 样例 2

改写前：

`选择保存以后系统会写入配置并重新加载服务。`

改写后：

`选择「保存」。系统随后写入配置并重新加载服务。`

检查点：区分人工动作和系统行为，不把系统行为误写成人工步骤。

#### 样例 3

改写前：

`如果设备温度超过允许范围，不要继续启动设备。`

改写后：

`如果设备温度超过允许范围，不要启动设备。`

检查点：保留条件和禁止关系，不补充未知温度值。

### API 文档

#### 样例 4

改写前：

`调用接口前应配置访问令牌，否则请求会返回认证错误。`

改写后：

`调用接口前，配置访问令牌。未配置访问令牌时，请求返回认证错误。`

检查点：前置条件和失败结果分开，未补充状态码。

#### 样例 5

改写前：

`请求成功后接口会返回任务 ID，后续可以使用这个 ID 查询处理状态。`

改写后：

`请求成功后，接口返回任务 ID。使用该任务 ID 查询处理状态。`

检查点：保持对象名称一致，避免无法定位的「这个 ID」。

#### 样例 6

改写前：

`请求失败时最多重试 3 次，每次间隔 5 秒。`

改写后：

`请求失败时，最多重试 3 次。每次重试间隔 5 秒。`

检查点：原有次数和间隔保持不变。

### 故障排查

#### 样例 7

改写前：

`页面无法打开时可能是网络问题，可以先检查浏览器是否能够访问其他站点。`

改写后：

`页面无法打开时，先检查浏览器能否访问其他站点。网络异常是可能原因之一。`

检查点：没有把可能原因写成确定原因。

#### 样例 8

改写前：

`查看服务日志并找到最早出现的错误，然后记录错误时间和请求 ID。`

改写后：

1. `查看服务日志，找到最早出现的错误。`
2. `记录错误时间和请求 ID。`

检查点：按执行顺序拆分动作，没有增加日志位置。

#### 样例 9

改写前：

`排查期间不要删除日志文件，因为后续分析还需要这些文件。`

改写后：

`排查期间，不要删除日志文件。后续分析仍然需要这些文件。`

检查点：保留禁止动作和原因。

### 产品介绍

#### 样例 10

改写前：

`平台提供任务创建、状态查询和结果下载能力。`

改写后：

`平台提供任务创建、状态查询和结果下载能力。`

检查点：原文已经清晰，不为追求变化而改写。

#### 样例 11

改写前：

`通过一站式能力赋能团队快速完成数据处理。`

改写后：

`平台集中提供数据处理功能，帮助团队快速完成数据处理。`

检查点：删除空泛的「一站式能力」和「赋能」，但保留原文已有的「快速」主张；不要擅自补充速度指标。

#### 样例 12

改写前：

`系统通常会在任务完成后发送通知。`

改写后：

`系统通常在任务完成后发送通知。`

检查点：保留「通常」表达的不确定程度。

## 自动检查边界

可以稳定自动检查：

- 确定错字
- 明确的术语大小写
- 机器可读内容是否被错误处理
- 项目词表中的确定映射

只应提示人工判断：

- 一个句子是否包含过多动作
- 条件是否应当提前
- 主语是否需要显式写出
- 代词是否有歧义
- 被动表达是否影响理解
- 文本是否过度简化
- 改写是否改变事实或确定程度

不要把句长、被动句、代词或语境词设置为无条件失败规则。自动检查工具只能提供提示，不能证明文本符合 ASD-STE100，也不能代替作者判断。
